## 1. Executive Summary & Core Principles

The Investor Profile & Personalization engine provides PortfolioMind with an authoritative, durable representation of the user's investment goals, psychological risk tolerance, financial balance-sheet capacity, investment policy (IPS), and decision preferences.

### Core Architectural Principles
1. **One User-Facing Profile Model:** A unified schema covering Goals & Financial Context, Risk Profile, Investment Policy Statement (IPS), and Preferences.
2. **Separation of Raw Answers vs Structured Interpretation:** User responses (including skips, notes, and timestamps) are immutably persisted in `investor_profile_answers`. The interpreted state is generated by a deterministic rules engine and staged in `investor_profile_drafts` before confirmation.
3. **Strict Separation of Risk Tolerance and Risk Capacity:** Psychological tolerance (emotional ability to endure paper drawdowns) and financial risk capacity (practical ability of the balance sheet to absorb loss without jeopardizing vital obligations) are modeled as distinct dimensions. **They are never collapsed into a single generic risk score.**
4. **Contradiction Engine:** Identifies tensions and conflicts between stated preferences and reality (Rules X01–X13). For example, Rule X01 flags high drawdown tolerance (40%+) when combined with near-term fixed liquidity withdrawals.
5. **Meaningful 100-Point Completeness & Capability Readiness:** Tracks coverage across 5 weighted domains (Goals: 20, Tolerance: 20, Resilience: 25, Liquidity: 20, Experience: 15) and exposes explicit readiness states (`READY`, `PARTIAL`, `LIMITED`, `UNAVAILABLE`) for analytical engines.
6. **Multi-Level Skipping & Non-Intrusive Defaults:** Users can skip any question, section, or the entire assessment. Skipped fields remain explicitly unknown; **no answers or assumptions are ever fabricated**.
7. **Material Version History & Immutability:** Confirmations create sequential, immutable versions (v1, v2, etc.) in `investor_profile_versions` with recorded provenance, source, and change rationale.
8. **Level 2 Copilot Integration:** Copilot reads profile data for context selection, but conversational changes (e.g., "My income is stable now and I can take more risk") produce a `LEVEL_2_CONFIRMATION_REQUIRED` proposal with old/new state diffs, requiring explicit confirmation before incrementing to a new material version and logging to `copilot_audit_logs`.
9. **Portfolio Setup Handoff:** Seamlessly hands off post-confirmation users to the existing Phase 3 Portfolio Import Engine (Chat, CSV, or Screenshot notice) without duplicating import architecture.

## 2. Database Model & Schema

All tables enforce multi-user isolation with foreign keys to `users.id` with `CASCADE` delete and PostgreSQL JSONB storage for structured flexibility.

```
                    ┌─────────────────────────┐
                    │          User           │
                    └────────────┬────────────┘
                                 │ 1:1
                    ┌────────────▼────────────┐
                    │     InvestorProfile     │  (authoritative active pointer)
                    └────────────┬────────────┘
         ┌───────────────────────┼───────────────────────┐
         │ 1:1                   │ 1:N                   │ 1:N
┌────────▼───────────┐  ┌────────▼───────────┐  ┌────────▼───────────┐
│InvestorProfileDraft│  │ InvestorProfile    │  │InvestorProfile     │
│                    │  │ Assessment         │  │Version (v1, v2...) │
└────────────────────┘  └────────┬───────────┘  └────────────────────┘
                                 │ 1:N
                        ┌────────▼───────────┐
                        │InvestorProfile     │
                        │Answer (C01-C12...) │
                        └────────────────────┘
```

### Table Definitions
1. **`investor_profiles`**: Anchor record holding `user_id`, `active_version_id` (FK to active `investor_profile_versions`), cached completeness score, analysis readiness flags, and last confirmed timestamp.
2. **`investor_profile_assessments`**: Stores assessment questionnaire lifecycle (`NOT_STARTED`, `IN_PROGRESS`, `COMPLETED`, `ABANDONED`), questionnaire version (`v1`), and `resume_question_id`.
3. **`investor_profile_answers`**: Immutably records every response, selected option codes, numeric inputs, optional user clarification text, locale, and `knowledge_state` (`KNOWN`, `SKIPPED`, `DECLINED`). Unique constraint on `(assessment_id, question_id, item_id)`.
4. **`investor_profile_drafts`**: Staging area for deterministic evaluation before user confirmation. Stores full structured JSONB with goals, risk, policy, preferences, issues, completeness, and readiness.
5. **`investor_profile_versions`**: Immutable material versions created whenever a draft is confirmed or an update is applied via settings or Copilot. Tracks `version_number` (1, 2, 3...), `previous_version_id`, `change_source` (`ONBOARDING`, `SETTINGS`, `COPILOT`, `PERIODIC_REVIEW`), `change_reason`, and complete snapshot.

## 3. Risk Engine: Separate Tolerance & Capacity

The evaluation engine (`InvestorProfileRulesEngine`) maintains strict separation between psychological willingness and financial capacity:

### Psychological Risk Tolerance
Evaluated from:
- **C08 (Drawdown Comfort):** `P05` (5%), `P10` (10%), `P15_25` (15-25%), `P30` (30%), `P40_PLUS` (40%+).
- **C09 (Market Stress Reaction):** `BUY_MORE` (Accumulate), `HOLD` (Stay course), `REVIEW` (Reassess), `EXIT` (Sell to cash).

Output Rating: `LOW`, `MODERATE`, `HIGH`, `VERY_HIGH`, or `MIXED` (if C08 and C09 conflict, triggering Rule X04).

### Financial Risk Capacity
Evaluated per goal based on balance sheet realities:
- **Time Horizon (C02):** Long (> 5-10 yrs) vs Short (< 1-3 yrs).
- **Goal Flexibility (C02/F01):** Flexible vs Fixed deadline.
- **Planned Withdrawals (C03/F01):** None vs Major near-term liquidity need.
- **Emergency Reserve Cushion (C04/C07):** < 3 months vs 3-6 months vs 6+ months.
- **Income Reliability (C05):** Stable surplus vs Variable/strained.
- **Loss Consequence (C07):** Permanent loss consequence (delay vs reduce vs unaffordable).

Output Status per goal:
- **`UNCONSTRAINED`**: Ample time horizon, comfortable cash reserve, no near-term forced sales.
- **`CONDITIONAL`**: Moderate cushion or flexible horizon requiring monitored risk.
- **`CONSTRAINED`**: Near-term fixed withdrawal commitments, insufficient emergency cushion, or catastrophic loss consequences.

### Contradiction Detection Rules
- **Rule X01 (Tolerance vs Capacity Divergence):** Triggered when stated psychological tolerance is `HIGH` or `VERY_HIGH` (e.g., C08 = `P40_PLUS`), but financial capacity is `CONSTRAINED` due to near-term liquidity commitments (< 18 months) or fixed non-deferrable goals.
- **Rule X03 (Emergency Reserve Cushion):** Triggered when illiquid or high-risk assets are held or planned with < 3 months emergency reserves.
- **Rule X04 (Tolerance vs Stress Reaction Conflict):** Triggered when claiming high risk appetite but indicating panic selling (`EXIT`) during market sell-offs.

## 4. Completeness & Capability Readiness

### 100-Point Weighted Completeness
Completeness is calculated deterministically across 5 domains without fabricating missing answers:
- **Goals & Financial Context:** 20 points
- **Risk Tolerance:** 20 points
- **Resilience & Risk Capacity:** 25 points
- **Liquidity & Cash Flow:** 20 points
- **Preferences & Experience:** 15 points
- **Total: 100 points**

### Capability Readiness Matrix
Each analytical module queries readiness to adapt its UI and insights:
| Capability | Condition for `READY` | Fallback / Quiet State |
|---|---|---|
| **Risk Analysis** | C08 and C09 answered | Displays general volatility warnings |
| **Capacity Analysis** | Horizon, withdrawals, and reserve band known | Uses conservative liquidity assumptions |
| **Target Allocation** | Risk capacity and primary goal known | Offers default balanced allocation templates |
| **Portfolio Fit** | Tolerance and restriction topics known | Generic diversification checks only |
| **Liquidity Analysis** | Planned withdrawals and emergency reserve known | Highlights missing reserve data |
| **Copilot Support** | Always `READY` | Tailors advice depth to profile completeness |
| **Research Relevance** | Asset experience (C10) known | Highlights standard research items |

## 5. Copilot Level 2 Write Integration

Copilot integrates with the Investor Profile via two mechanisms:

### Read Context Injection (`CopilotContextEngine`)
When intent classification detects requests for risk, allocation, or portfolio advice, `CopilotContextEngine` injects the active profile:
```json
{
  "has_investor_profile": true,
  "version_number": 2,
  "goals": { "primary_kind": "WEALTH_ACCUMULATION", "horizon": "H5_10" },
  "risk": {
    "tolerance_summary": "HIGH",
    "drawdown_comfort": "P30",
    "capacity_status": "UNCONSTRAINED"
  },
  "policy": { "restriction_topics": ["TOBACCO"] }
}
```

### Write Execution (`CopilotWriteExecutor`)
Casual conversational statements (e.g., "My income is stable now and I can take more risk"):
1. Intent classified as `IntentType.POLICY_CHANGE`.
2. A `CopilotActionProposal` is generated with `permission_level = LEVEL_2_CONFIRMATION_REQUIRED` and `action_type = UPDATE_INVESTOR_PROFILE`.
3. Proposal contains explicit old vs new state diff.
4. **Zero mutations occur before confirmation.**
5. Upon user confirmation (`POST /api/copilot/proposals/{id}/confirm`):
   - Atomically updates profile via `InvestorProfileService.apply_profile_update`.
   - Increments material version to next sequential integer.
   - Sets `change_source = "COPILOT"`.
   - Records durable `CopilotAuditLog` entry.

## 6. Frontend User Experience & Routes

1. **`/onboarding` (`OnboardingPage.tsx`):**
   - Clean, step-by-step card layout for questions C01 through C12.
   - Question-level skipping ("Skip question") and assessment-level skipping ("Skip and go to Dashboard").
   - Live progress indicator.
   - Review draft screen with completeness score, capability badges, and contradiction alerts (X01).
   - Post-confirmation portfolio setup handoff modal.
2. **`/settings/investor-profile` (`InvestorProfilePage.tsx`):**
   - Comprehensive view of current confirmed version.
   - Separate Psychological Tolerance and Financial Risk Capacity cards.
   - Investment Policy Statement (IPS) parameters and exclusions.
   - Interactive Capability Readiness breakdown.
   - Material version history audit log with timestamps and sources.
3. **`/settings` (`SettingsPage.tsx`):**
   - Direct navigation card to Investor Profile and retake assessment flow.
4. **Dashboard Banner (`InvestorProfileBanner.tsx`):**
   - Quiet, dismissable banner for unconfirmed or low-completeness users.
   - Prominent policy alert banner when contradiction X01 is active.
5. **Registration (`RegisterPage.tsx`):**
   - Routes newly registered users to `/onboarding` to encourage immediate profile setup while preserving voluntary skipping.
